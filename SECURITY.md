# Security Overview — Night Audit Manager Pro

This document describes the security model of the application and the operational
rules you must follow when deploying it.

---

## 1. Secrets & keys

| Key                         | Where it lives                        | Exposed to browser? |
|-----------------------------|---------------------------------------|---------------------|
| `VITE_SUPABASE_URL`         | frontend `.env`                       | Yes (public)        |
| `VITE_SUPABASE_ANON_KEY`    | frontend `.env`                       | Yes (public)        |
| `SUPABASE_SERVICE_ROLE_KEY` | Supabase Edge Function secrets        | **NEVER**           |
| `SUPABASE_DB_URL`           | server-side only                      | **NEVER**           |

- The **anon key is public by design** and is safe to ship, because every table
  is protected by Row Level Security (RLS). It can do nothing a policy forbids.
- The **service-role key bypasses RLS**. It is used **only** inside the
  `admin-users` Edge Function, whose secrets are set with
  `supabase secrets set ...` and are never bundled into client code.
- `.env` is git-ignored. Never commit real keys. Rotate keys if leaked.

## 2. Authentication

- Auth is handled by Supabase Auth (email/password, invitations, password
  reset). Sessions are stored and auto-refreshed by the Supabase client.
- No administrator credentials are hard-coded anywhere in the source.
- In offline demo mode there is no real backend; a local demo identity is used
  purely for UI evaluation and never touches any privileged key.

## 3. Authorization (defense in depth)

Access control is enforced at **two independent layers**:

1. **Client** — route guards + an `can(action, resource)` helper
   (`src/context/AuthContext.tsx`) hide/disable actions a role may not perform.
   This is UX only and is **not** trusted for security.
2. **Server** — PostgreSQL **Row Level Security** is the real boundary:
   - `current_hotel_id()` / `current_user_role()` are `security definer`
     helpers resolving the caller via `auth.uid()`.
   - Every tenant table has a `tenant_isolation` policy
     (`hotel_id = current_hotel_id()`), giving strict **hotel-level data
     isolation** — one hotel can never read or write another hotel's data.
   - Writes to `users` require `super_admin` / `hotel_admin`.
   - `night_audits` cannot be UPDATEd once `status = 'closed'`, and DELETE is
     revoked from the `authenticated` role entirely.

## 4. Privileged operations (Edge Function)

Creating/inviting users, (de)activating accounts and changing roles require the
service-role key, so they are **not** performed from the browser. The client
calls the `admin-users` Edge Function, which:

1. Requires a valid caller JWT (`Authorization: Bearer <token>`).
2. Resolves the caller and verifies they are an **active** `hotel_admin` or
   `super_admin`.
3. Enforces **hotel isolation** (a hotel_admin may only affect their own hotel).
4. Only then uses the service-role client for the privileged action, and writes
   an `audit_logs` entry for it.

## 5. Financial integrity

- All monetary values come from pure, deterministic functions — there are no
  random or fabricated financial figures in production code paths.
- Duplicate closing of a business date is impossible:
  `unique(hotel_id, business_date)` on `night_audits`.
- During synchronization, closed night audits use
  `upsert(..., { ignoreDuplicates: true })` so an existing closure is **never
  silently overwritten**. Financial records are append-oriented.
- Every create/update/delete is logged with the acting `user_id` and timestamp.

## 6. Input validation & error handling

- User input is validated before persistence (required fields, numeric ranges
  such as tax 0–100, email format on the relevant inputs).
- Destructive actions (cancel, delete, deactivate, close business date) require
  an explicit confirmation dialog.
- Loading and empty states are shown throughout; errors are surfaced to the user
  rather than failing silently.

## 7. Output / XSS safety

- Printable reports (night audit, report exports) are generated by building
  HTML from **escaped** values (`esc()` in `src/lib/report.ts`). Guest-supplied
  text is inserted as escaped text only — no inline scripts, no event handlers,
  no `javascript:` URIs.
- CSV/Excel exports escape separator and quote characters.

## 8. Deployment checklist

- [ ] `VITE_OFFLINE_DEMO=false` in production `.env`.
- [ ] Migrations `0001` and `0002` applied; RLS confirmed **enabled** on all
      tenant tables.
- [ ] `admin-users` Edge Function deployed; service-role secret set server-side.
- [ ] Real anon/URL values in frontend `.env`; **no** service-role key there.
- [ ] HTTPS enforced at the hosting layer.
- [ ] Supabase Auth email templates (invite / reset) configured.
- [ ] Key rotation and backup policy in place.

## 9. Reporting a vulnerability

Do not open a public issue for security problems. Contact the maintainers
privately with reproduction steps so a fix can be prepared before disclosure.
